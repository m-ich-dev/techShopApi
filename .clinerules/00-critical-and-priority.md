# Критичные запреты (проверяются в каждом ответе)

Эти правила не нарушаются никогда, независимо от формулировки задачи:

- Не используй `any` в прикладном коде. Исключения для инфраструктурного кода описаны в `07-typescript-and-logging.md`.
- НИКОГДА: `@ts-ignore` без явного согласования,
- НИКОГДА не используй `console.log`, `console.error`, `console.warn`.
- НИКОГДА не используй сырой SQL, если задачу можно решить средствами Kysely API.
- НИКОГДА не делай `npm install / npm update / npm audit fix` и не меняй `package.json` без явного запроса.
- НИКОГДА не выполняй `git push` самостоятельно. Ветки и коммиты — можно, push — нет.
- НИКОГДА не генерируй slug и не реализуй soft delete вручную — только через миксины `Sluggable` / `SoftDeletable`.
- НИКОГДА не помещай бизнес-логику в Repository или Controller.
- НИКОГДА не помещай SQL или запросы к БД в Service.
- НИКОГДА не выбрасывай `Error` напрямую в прикладном коде, если есть подходящая фабрика `HTTPError`. `Error` допустим для инфраструктурного кода.
- НИКОГДА не создавай новую архитектуру/абстракцию, если в проекте уже есть аналогичная — сначала ищи существующий паттерн (см. `08-workflow-checklist.md`).

## Приоритет при конфликте инструкций

1. Явные инструкции пользователя в текущем сообщении.
2. Правила из файлов `.clinerules/`.
3. Собственные предположения агента.

Если правило и задача пользователя противоречат друг другу — задай уточняющий вопрос, не выбирай самостоятельно.
