# Service

Для сервисов, которым требуется генерация slug, используй миксин `GenerateSlug`.

Пример:

```ts
export default class CategoryService extends GenerateSlug(Service)
```

Метод `generateSlug(repository, fields)` используется только внутри сервисов. Логика формирования slug относится к бизнес-операции и не дублируется в контроллерах или репозиториях.

Repository предоставляет только необходимые методы доступа к данным, например `lastSlugIndex(baseSlug)`. Repository никогда самостоятельно не генерирует slug.

# Repository

Все репозитории наследуются от абстрактного `Repository`.

Правила:

- Используй существующие методы базового класса, если они подходят. Не дублируй уже существующую функциональность.
- Repository занимается исключительно запросами к БД, без бизнес-логики.
- Если репозиторий может работать со slug и soft delete — оборачивается в соответствующие миксины `Sluggable` и `SoftDeletable`.

Пример:

```ts
export default class CategoryRepository extends SoftDeletable(Sluggable(Repository<'categories'>))
```

- Если сущность поддерживает soft delete — используй `SoftDeletable`, не реализуй его вручную. Используй существующий метод `softDelete()`.

# Dependency Injection

Проект использует DI через контейнер (`src/boot/containers`):

- Контроллеры получают сервисы через контейнер.
- Сервисы получают репозитории через контейнер.

Не создавай зависимости через `new` внутри бизнес-кода, если они могут быть получены через контейнер. Новая сущность обязательно регистрируется в соответствующем контейнере (`controllers.container.ts`, `services.container.ts`, `repositories.contrainer.ts`).

# Ошибки

Для бизнес-ошибок используй `HTTPError` (`src/boot/http/http.error.ts`).

- Не выбрасывай обычный `Error`, если существует подходящая фабрика `HTTPError`.
- `Error` допустим для инфраструктурного кода. Например:

```ts
export default abstract class Resource {
    public static transform(data: any): any {
        throw new Error("transform must be implemented");
    }
```

- Используй существующие фабричные методы. Не добавляй новые фабрики без явного запроса — если подходящей нет, сначала предложи её пользователю.

# Resources

Контроллеры не преобразуют модели в JSON самостоятельно.

- Формирование ответа — только через соответствующий Resource (`src/http/v1/.../resources`).
- Если Resource уже существует — используй его, не дублируй сериализацию в контроллере.
- Если Resource для сущности отсутствует, а формат ответа нетривиален — создай его по аналогии с существующими (`brand.resource.ts`, `category.resource.ts`).

# Request

Валидация входящих данных располагается только в Request-классах (`src/http/v1/requests`), на базе zod.

- Не выполняй ручную валидацию в контроллерах или сервисах.
- Используй существующие Request-классы, если задача укладывается в имеющуюся структуру.
