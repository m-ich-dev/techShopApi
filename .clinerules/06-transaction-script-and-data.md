# Transaction Script

Проект использует паттерн Transaction Script в сервисном слое.

- Каждый публичный метод сервиса представляет законченную бизнес-операцию.
- Если метод выполняет более одного изменения БД — используй транзакцию Kysely.

Примеры операций, требующих транзакции:

- insert + insert
- insert + update
- update + delete
- insert + запись в pivot-таблицу

Любые связанные изменения выполняются внутри одной транзакции.

# Работа с Kysely

- Используй только API Kysely. Сырой SQL не используется, если это можно выразить средствами Kysely.
- Предпочитай типобезопасные запросы, переиспользование query builder, существующие helper-методы проекта (`jsonObjectFrom`, `jsonArrayFrom` и т.п.).

# Миграции и сиды

- Миграции (`src/database/migrations`) создаются только новыми файлами с корректным timestamp-префиксом по существующему шаблону именования.
- Не редактируй уже применённые (существующие) миграции задним числом — для изменения схемы создавай новую миграцию.
- Изменения в сидах (`src/database/seeds`) вносятся только по явному запросу.

# Тесты

- Проект использует Vitest (`src/tests`).
- При изменении логики в Service, которая покрыта существующими тестами — обнови соответствующий тест.
- При добавлении новой бизнес-операции в сложную сущность (`domain`, см. `04-architecture-layers.md`) — предложи тест-кейсы, даже если пользователь явно не просил.
- Не удаляй и не отключай существующие тесты для того, чтобы задача "прошла" — если тест ломается, разберись в причине и сообщи пользователю.
